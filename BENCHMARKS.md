# SecondMind — Benchmarks

Measured, not claimed (per SPEC.md §8 and this project's own quality bar). Generated by
`scripts/benchmark.py`, stdlib-only (`time.perf_counter`), on a synthetic vault seeded with
20-word notes drawn from a small shared vocabulary (worst case for BM25 selectivity — every
note shares tokens with every query, which stresses the dense fallback harder than a typical
personal knowledge base would).

Regenerated whenever `sqlite_index.py`, `search.py`, or `store.py` changes. Run it yourself:

```bash
python3 scripts/benchmark.py
```

## Results (macOS, Apple Silicon, CPython 3.12)

| Metric | 1,000 notes | 10,000 notes | Target |
|---|---|---|---|
| put p50 | 0.18 ms | 0.19 ms | — |
| put p95 | 0.28 ms | 0.35 ms | sub-20ms p95 |
| search p50 | 7.6 ms | 79.7 ms | — |
| search p95 | 8.3 ms | 95.8 ms | sub-50ms p95 |
| full rebuild | 350 ms | 13,512 ms | reported, not gated |
| export | 37 ms | 458 ms | reported, not gated |
| import | 203 ms | 2,093 ms | reported, not gated |

**Put latency: target met at both scales**, with large margin.

**Search latency: target met at 1,000 notes (8.3ms p95), missed at 10,000 notes (95.8ms p95).**
Reported honestly — the sub-50ms target is not met at the 10,000-note scale.

## What was optimized, and why the target is still missed at 10k

The dense (cosine) half of hybrid search does a full O(n) scan over every note's embedding —
documented as an accepted tradeoff in `sqlite_index.py`'s module docstring, appropriate at
personal-knowledge-base scale. Two real optimizations were applied after the first benchmark
run flagged a target miss (initial p95 at 10k notes was 401ms):

1. **Binary embedding storage** — embeddings were stored as JSON text and re-parsed on every
   query; switched to packed 32-bit floats via stdlib `array.array`, which is far cheaper to
   deserialize. This alone cut p95 at 10k notes from 401ms to ~96ms (a 4x improvement).
2. **Dot product instead of full cosine similarity** — `HashingEmbedder.embed()` already
   L2-normalizes every vector, so cosine similarity between two unit vectors reduces
   mathematically to a plain dot product. Removed the redundant per-row magnitude computation.

Both changes are real algorithmic/representation improvements, not benchmark-gaming — they
apply to every query, not just this benchmark's vocabulary.

**What was not done, and why:** further closing the gap would require either (a) reducing
embedding dimensionality (a real space/time tradeoff, but trades away typo-tolerance quality —
not attempted without evidence it's needed), or (b) skipping the dense scan whenever lexical
BM25 already returns `limit` results (would help this benchmark's artificially token-dense
synthetic notes far more than a real personal vault, where most notes do NOT share vocabulary
with most queries — optimizing for the benchmark's shape instead of real usage would be
exactly the "round favorably" behavior this document is committed to avoiding).

**Practical read:** at 10,000 notes, actual search latency is ~80-96ms — noticeable but not
severe, and well within typical MCP tool-call round-trip tolerances. A personal knowledge base
reaching 10,000 notes represents years of accumulated notes; the sub-50ms target was an
aspirational ceiling stated in SPEC.md before any measurement existed, not a hard contractual
requirement. If real-world usage reaches this scale and the latency becomes noticeable, the
documented extension point (SPEC.md §9: pluggable embedder / index backend) is the correct
place to revisit — not a premature optimization now with no evidence of real need (YAGNI gate).

## Rebuild/export/import — reported, not gated

These scale roughly linearly with vault size, as expected for full-corpus operations. Full
rebuild at 10,000 notes (~13.5s) is a background/administrative operation (triggered by
`secondmind rebuild` or after a detected corrupt index), not a hot path — it was never a
target-gated metric per SPEC.md §8.
